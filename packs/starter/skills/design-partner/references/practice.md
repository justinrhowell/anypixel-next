# Design from the task

Start with what a person needs to accomplish. Establish the primary action, required information, constraints, and existing patterns before changing style. Keep a useful existing design when the evidence does not support replacing it.

Review hierarchy and content together: what should be noticed, read, compared, or acted on first? Explain why the proposed change helps that job. “Use more whitespace” is too vague; “separate the optional fields from the required invitation step” connects a change to the task.

Reuse existing components and tokens. When a departure is useful, explain its cost and scope. Inspect applicable loading, empty, error, success, responsive, keyboard, and permission states. Do not claim to have inspected an interaction from a screenshot.

Use measured evidence for verifiable conditions. Label visual interpretation as inference, and user preference as a preference. An automated accessibility check can reveal problems but cannot establish complete accessibility or usability.

When exploring, compare alternatives with different information or interaction structures. Recommend one against the goal and explain what would change the recommendation. For a small reversible edit, proceed under the user's existing authorization rather than introducing a ceremony.

Record a decision with a reason and scope so a later task can reuse it. A preference for dense invoice tables is not a rule that all lists must be tables. A later user instruction can replace an old choice. Accepted preferences are not experimental proof of better usability.

This is original starter guidance, currently experimental. Independent pilot evidence belongs in the public evaluation record before stronger quality claims.
